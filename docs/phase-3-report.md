# Фаза 3: права и изоляция данных

Статус на 1 ноября 2026: **начата; Gate 3 не пройден**. По решению пользователя staging отложен, работа начата до полного закрытия проверок фазы 2.

## Выполнено

- Созданы тип `Scope`, проверка корректной пары family/owner и сравнение scope для будущих связей и неизменности владельца.
- Созданы серверные проверки пользователя через `getUser`, активного членства, роли и принадлежащего владельцу личного scope. Для семейных финансов назначены права admin/member; child по умолчанию запрещён. Эти вспомогательные проверки пока не подключены ко всем будущим модулям и сами по себе не заменяют RLS.
- Серверная проверка семейного scope требует конкретную capability вместе с активным членством; неизвестная или отсутствующая capability не предоставляет доступ. Для личного scope проверяется владелец. Доступ child к личным модулям должен дополнительно определяться правилами соответствующего модуля.
- Действия администратора по приглашению, отзыву, добавлению детского профиля и смене роли проверяют активное членство и право на сервере; базы данных повторно проверяют права в своих функциях. Проверены отказы member/child и успешное действие admin в локальном браузере.
- Исключение другого участника требует серверного подтверждения роли администратора; собственный выход доступен активному участнику. База повторно проверяет права и последнего администратора. В локальном браузере подтверждены отказ последнему администратору, исключение второго участника и немедленный отзыв доступа к семье при сохранённой сессии. Тестовые аккаунты и семья удалены.
- Детский аккаунт в таблице участников и функции `family_roster` видит только собственную активную запись. Взрослый участник видит активный состав своей семьи. Проверка принадлежности использует `SECURITY DEFINER` в закрытой схеме и не вызывает рекурсивную RLS-политику.
- Ограничение внешнего ключа запрещает связывать профиль участника с членом другой семьи. Оба изменения применены и проверены локально и в облачной базе.
- SQL-проверка на локальной и облачной Supabase создаёт две семьи во временной транзакции и проверяет изоляцию, роль child, роль взрослого участника и прекращение доступа после исключения. Тестовые записи откатываются.
- Проверены RLS и запрет анонимных прав на все текущие пользовательские таблицы в `public` и `private`, а также отсутствие прямого изменения семейных таблиц и выдачи хэша приглашения. Для сервисной роли добавлен доступ к схеме `private` для вызова уже разрешённых функций без прямых прав чтения приватных таблиц.
- Добавлены SQL-функции проверки корректности и совпадения scope, доступа владельца/участника, роли и неизменности области записи. Они применены локально и в рабочей базе. Временная таблица с RLS проверяет CRUD для двух семей и нескольких владельцев, подмену владельца и смену family/private. Это тестовый образец политики, а не готовая политика для будущих продуктовых таблиц.
- В GitHub Actions job security-db с чистой базой и SQL-проверкой успешно прошёл для коммита 3b1dcf4.
- Через локальный Storage API подтверждено, что гость и другой пользователь не могут скачать чужой аватар или получить подписанную ссылку; другой пользователь не может загрузить файл в чужую папку или удалить чужой файл. Тестовые пользователи и файл удаляются после проверки. Рабочий Storage API отдельно не тестировался.
- 03.11.2026 локально проверены доступ взрослого к финансам, отказ ребёнку на всех финансовых страницах и аналитике, скрытие ссылок, а также SQL-проверка изоляции с откатом. Страницы пока не содержат финансовых данных; новые изменения ещё не проверены в GitHub CI.
